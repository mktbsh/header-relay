# 監査ログのレベル絞り込みを読み出しクエリで行い、`by_level` indexを使わない

## 背景

管理画面のAudit Logsは、記録を新しい順に最大200件取得して全件表示する（`src/entrypoints/manage/use-audit-log.ts`）。
保持上限は1000件・7日である（`src/lib/storage/audit-retention.ts`）。

記録の大半は`origin_matched`（debug）で、一致したProfileごと・対象リクエストごとに1件出る（`src/lib/lifecycle/runtime-session.ts:262`）。
原因を示すwarnとerrorは5箇所からしか出ない。

利用者は記録量の多さでログを読むことをやめている。深刻度による絞り込みを追加する。

## 決定

絞り込みは、IndexedDBからの読み出し時に適用する。
`by_ts` indexのカーソル走査に深刻度の判定を加え、条件に一致した記録を新しい順に`limit`件集める。

既存の`by_level` indexは使わない。

## 理由

### クライアント側で絞り込まない

取得済みの200件を画面側で絞り込む実装は、この機能が最も必要な場面で0件を返す。

リクエストの多い画面では、最新200件がすべてdebugとinfoで埋まりうる。
その状態で「warn以上」を選んでも、取得済みの200件にwarnとerrorが含まれないため結果は0件になる。
記録はIndexedDBに残っているのに画面には存在しない、という最悪の結果になる。

読み出し側で絞り込めば、保持している1000件全体が対象になる。

### `by_level` indexで範囲クエリを組めない

IndexedDBのキー順序は文字列順であり、levelの値は `debug` < `error` < `info` < `warn` の順に並ぶ。
深刻度の順序は `debug` < `info` < `warn` < `error` であり、両者は一致しない。

このため「warn以上」を`IDBKeyRange`で表現できない。

`by_level`から深刻度ごとに複数回引いて結果をマージする方法は取れるが、
新しい順という並び順を保つために取得後の再ソートが必要になり、`limit`件で打ち切る条件も複雑になる。

`by_ts`のカーソル走査に判定を1つ加えるほうが、並び順も打ち切りもそのまま維持できる。

### 走査コストを許容できる

「errorのみ」のように一致件数が少ない条件では、カーソルは保持上限の1000件すべてを走査してから`limit`件未満で終わる。

既存の`add()`は書き込みのたびに全件を取得して保持期間を適用しており（`audit-db.ts`の`pruneRetention`）、
同等の走査をすでに毎回行っている。読み出し側の1000件走査が新たなボトルネックになる可能性は低い。

## 影響

`AuditPort.recent`の引数に深刻度の下限を追加する。
IndexedDBアダプターとin-memoryアダプターの両方が同じ判定を共有する。

深刻度の順序は`src/lib/domain/audit-level.ts`に単一の順序付き定数として置き、`AuditLogLevel`型をそこから導出する。
順序の配列と型が別々に定義されていると、レベルを追加したときに片方だけ更新される。

`by_level` indexは残す。削除にはIndexedDBのバージョン更新が必要で、
そのコストに見合う利点がない。将来「特定の1レベルだけ」を引く要件が出た場合には使える。

## 代替案

- **取得済み200件のクライアント側フィルタ**：実装は最小だが、上記のとおり必要な場面で機能しない。
- **`by_level`を深刻度ごとに複数回引いてマージ**：indexを活かせるが、並び順の再構築と打ち切り条件が複雑になる。
- **`origin_matched`の記録をやめる**：記録量そのものが減るが、どのProfileがどのリクエストに反応したかを確かめる唯一の記録を失う。

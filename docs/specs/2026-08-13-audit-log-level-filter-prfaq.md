# 監査ログのレベル絞り込み PR/FAQ

## 文書の目的

この文書は、Header Relayの監査ログへ追加するレベル絞り込みについて、利用者が得る結果から必要な動作を定義する。

## 顧客の5つの質問

### 1. 顧客は誰か

Header Relayでローカル環境または検証環境のAPIを検証する開発者のうち、ヘッダーが期待どおり送信されない、またはレスポンスから取得されない原因を追うために監査ログを開く利用者。

- 対象利用者の定義：**事実**（出典：`CONTEXT.md`、既存のCookie機能PR/FAQで定義済み）
- そのうち監査ログを開くのが原因追跡時に限られること：**仮説**（利用実態の計測はない）

### 2. 顧客のどんな課題・機会に取り組むのか

監査ログの記録量が多く、読む気が失せる。

- 課題の存在：**事実**（出典：ユーザーの観測「量が多くて見る気が失せる」）
- 最大量のイベントが`origin_matched`（debug）であり、一致したProfileごと・対象リクエストごとに1件記録されること：**事実**（出典：`src/lib/lifecycle/runtime-session.ts:262`）
- セッションが変化するたび`config_compiled`と`dnr_rules_synced`（info）が追加されること：**事実**（出典：`src/lib/dnr/rule-sync.ts:80,140`）
- 原因を示すwarnとerrorが低頻度であること：**事実**（出典：`runtime-session.ts:224`、`rule-sync.ts:66,163,182,198`の5箇所のみ）
- 管理画面が取得するのは最新200件であり、保持上限は1000件・7日であること：**事実**（出典：`src/entrypoints/manage/use-audit-log.ts:11`、`src/lib/storage/audit-retention.ts`）
- リクエストの多いページでは、warnまたはerrorが最新200件の外へ押し出されて画面に現れない場合があること：**仮説**（コードから導いた結論であり、実際の発生は未計測）

### 3. 最も重要な顧客ベネフィットは何か

原因になりうる記録だけを画面に残せる。

**事実**（出典：ユーザーの決定）

### 4. 顧客がそれを望んでいると、どうやって知ったか

ユーザー自身がHeader Relayの監査ログを使い、記録量の多さで読むことをやめている。

**事実**（出典：ユーザーの観測）

### 5. 顧客体験はどのようなものになるか

Settings画面のAudit Logsで、表示するログの深刻度をセレクトから選ぶ。「info以上」を選ぶと`origin_matched`が消え、「warn以上」を選ぶと原因候補だけが残る。選択は保存せず、開き直すと「すべて」に戻る。

**事実**（出典：ユーザーの決定）

## 将来の発表文

（発表日：2026-08-20）

### Header Relay、監査ログから原因になりうる記録だけを表示可能に

**Header Relayの監査ログに深刻度の絞り込みが加わり、開発者はリクエストごとの記録に埋もれずに失敗の記録へ到達できるようになりました。**

Header Relayは、ローカル環境と検証環境のAPI検証でリクエストヘッダーを中継するChrome拡張機能です。本日の更新で、管理画面のAudit Logsに表示レベルの選択を追加しました。

Header Relayの監査ログは、対象オリジンに一致したリクエストを1件ずつ記録します。この記録は、どのProfileがどのリクエストに反応したかを確かめるときに役立ちます。一方で、リクエストの多い画面を開くと一致の記録が大半を占め、確かめたかった失敗の記録がその中に紛れます。記録が一定量を超えると、開発者はログを読むこと自体をやめてしまいます。

新しい表示レベルの選択では、「すべて」「info以上」「warn以上」「errorのみ」から表示範囲を選べます。「info以上」を選ぶとリクエストごとの一致記録が消え、設定の反映と値の取得だけが残ります。「warn以上」を選ぶと、Cookieの解析失敗とルール同期の失敗だけが残ります。絞り込みは保存済みのログ全体に対して行うため、直前のリクエストで押し流された失敗の記録も見つけられます。

「監査ログは、うまくいかないときに開くものです」とHeader Relayの開発者は述べています。「その瞬間に必要なのは1件のerrorであって、直前の200件の正常な記録ではありません。読む気が失せる時点で、ログは診断の道具として機能していません」

利用を始めるには、管理画面のSettingsからAudit Logsを開き、見出しの横のセレクトで深刻度を選びます。設定は不要で、既存のログにもそのまま適用されます。選択は保存されないため、次に開いたときは従来どおりすべての記録が表示されます。

「Cookieが送られない原因を探していたとき、解析失敗の記録があるはずなのに見つけられませんでした」とAPI開発者は述べています。「warn以上に切り替えたら1件だけ残って、それが答えでした」

Header Relayは Chrome ウェブストアから入手できます。監査ログに記録する内容と保存期間は今回の更新で変更していません。

## 利用者から想定される質問

### 何を選べますか

「すべて」「info以上」「warn以上」「errorのみ」の4段階です。**事実**（出典：ユーザーの決定）

段階選択のため、「warn以上」にはerrorも含まれます。深刻度の順序は debug、info、warn、error です。

### 既定はどれですか。選択は残りますか

既定は「すべて」で、現在の表示と変わりません。選択は保存せず、画面を開き直すと「すべて」に戻ります。**事実**（出典：ユーザーの決定）

監査ログは、まず記録の全体量を認識するための画面です。記録が多いこと自体が、拡張機能がどれだけのリクエストに反応しているかを示す情報にあたります。絞り込みは、その全体を見たうえで利用者が意図して行う操作と位置づけます。

このため、既定では絞り込みません。選択も保存せず、開くたびに全体量から始めます。

### 絞り込むと、古いerrorも見つかりますか

見つかります。**事実**（出典：ユーザーの決定）

絞り込みは、画面が取得済みの記録に対してではなく、保存済みの記録全体に対して行います。リクエストの多い画面で正常な記録が大量に追加され、失敗の記録が最新200件の外へ出た場合でも、「warn以上」を選べば表示されます。

保存の上限である1000件・7日を超えて破棄された記録は復元できません。

### 一度に表示される件数は変わりますか

変わりません。絞り込んだ結果のうち、新しいものから最大200件を表示します。**事実**（出典：ユーザーの決定）

### 記録される内容やプライバシーの扱いは変わりますか

変わりません。**事実**（出典：本機能は表示のみを変更する）

監査ログに記録する項目、保存先、保存期間（IndexedDBへ最大1000件・7日）、リクエストURLを永続化しない方針は従来どおりです。絞り込みは記録の削除ではなく表示の選択であり、選択を戻せば同じ記録が再び表示されます。

### 記録そのものを減らすことはできますか

現時点ではできません。**未回答**

記録の量そのものを減らす設定は今回の対象外です。表示の絞り込みで十分かどうかは、この機能を出したあとに判断します。

## 開発と運用で確認する質問

### なぜ取得済みの200件をクライアント側で絞り込まないのか

取得済みの200件を絞り込む実装は、この機能が最も必要な場面で何も表示しないためです。

管理画面が取得するのは新しい順に200件です。リクエストの多い画面では、この200件がすべて`origin_matched`と`headers_captured`で埋まりえます。その状態でクライアント側の絞り込みを「warn以上」にしても、取得済みの200件にwarnとerrorが含まれないため結果は0件になります。探している記録は保存されているのに見つからない、という最悪の結果になります。

そのため、絞り込み条件をIndexedDBの読み出しへ渡し、条件に一致する記録を新しい順に200件集めます。**事実**（出典：ユーザーの決定）

### `by_level` indexを使うのか

使いません。**事実**（出典：IndexedDBのキー順序）

`audit_logs`ストアには`by_level` indexが定義済みですが（`src/lib/storage/audit-db.ts:25`）、IndexedDBのキー順序は文字列順であり、`debug` < `error` < `info` < `warn` になります。深刻度の順序（debug < info < warn < error）と一致しないため、「warn以上」を範囲クエリで表現できません。

代わりに、現行の`recent()`が使っている`by_ts` indexのカーソル走査（`audit-db.ts:76-88`）へ、深刻度の判定を加えます。indexの追加は不要で、新しい順という並び順も変わりません。

### 走査コストは許容できるか

許容できます。**仮説**（設計上の見積もりであり、実測はしていない）

「errorのみ」のように一致件数が少ない条件では、カーソルが保存上限の1000件すべてを走査してから200件未満で終わります。ローカルのIndexedDBに対する1000件の走査は、利用者が押したボタンへの応答として問題になる規模ではありません。

なお、既存の`add()`は書き込みのたびに全件を取得して保持期間を適用しており（`audit-db.ts`の`pruneRetention`）、同等の走査をすでに毎回行っています。読み出し側で1000件を走査することが新たなボトルネックになる可能性は低いと判断します。

### 新しい権限やスキーマ変更は必要か

不要です。**事実**（出典：本機能は既存ストアの読み出し条件のみを変更する）

`AppConfig`のスキーマ、監査ログの保存形式、manifestの権限はいずれも変更しません。選択状態を保存しないため、保存領域も使いません。

### このアイデアが失敗するとしたら、原因は何か

**既定を「すべて」にし、かつ選択を保存しないため、監査ログを開いた直後の体験が現在と変わらない点です。**

この機能が解こうとしている課題は「量が多くて読む気が失せる」ことです。しかし利用者が最初に目にするのは、従来どおりすべての記録が並んだ画面です。読む気が失せる状態そのものは残り、利用者は毎回セレクトを操作して初めて課題が解消されます。

この摩擦を承知のうえで、既定は「すべて」・選択は保存しないを採ります。**事実**（出典：ユーザーの決定）

監査ログの役割は、まず記録の全体量を利用者へ提示することだと位置づけるためです。記録が多いこと自体が、拡張機能が反応しているリクエストの量を示す情報にあたります。既定で絞り込む、あるいは前回の絞り込みを引き継ぐ設計は、この全体量を利用者から隠します。絞り込みは、全体を見たうえで意図して行う操作に限ります。

したがって、この機能が引き受ける課題は「読む気が失せる状態を最初から作らないこと」ではなく、「読む気が失せた利用者が、そこから1操作で原因へ到達できること」です。

もう一つの失敗経路は、真の原因が絞り込みの不在ではなく`origin_matched`を記録しすぎていることである可能性です。この場合、正しい対処は表示の絞り込みではなく記録量そのものの削減になります。ただし`origin_matched`は「どのProfileがこのリクエストに反応したか」を確かめる唯一の記録であり、削除すると別の診断ができなくなります。表示の絞り込みは、記録を残したまま量の問題だけを解く点で先に試す価値があると判断します。**仮説**

### なぜ我々がやるのか、なぜ今か

監査ログは既にHeader Relayの唯一の診断手段であり、それが読まれていないことをユーザー自身が観測しています。**事実**（出典：ユーザーの観測）

実装は既存のカーソル走査への条件追加と、セレクト1つの追加に収まります。着手の障壁が低く、この後に予定しているProfile複製・設定の書き出しと読み込み・キーボードショートカットのいずれとも依存関係がありません。**事実**（出典：ユーザーの決定した実施順）

### リリース時の変更種別は何か

利用者が使える機能を追加するため、`header-relay`のpatch changesetを同梱します。表示の選択肢が増えるだけで、既定の見え方と保存内容は変わりません。

利用者向け文言は`public/_locales/en/messages.json`へ英語で定義し、同じコミットで対応する全ロケール（ja / ko / es / fr / de / zh_CN / zh_TW）へ反映します。

## 判定

**進める**

### 根拠

最重要ベネフィット「原因になりうる記録だけを画面に残せる」は、ユーザー自身の観測（記録量の多さで読むことをやめている）と、コード上の事実（`origin_matched`が一致Profileごと・リクエストごとに1件、warnとerrorは5箇所のみ）で裏付けられています。

このアイデアを潰しうる質問「開いた直後の体験が変わらないため、読む気が失せる状態が残るのではないか」にも答えが出ました。監査ログの役割を「まず記録の全体量を提示すること」と定めたうえで、この機能が引き受ける範囲を「全体量を見た利用者が1操作で原因へ到達できること」に限定します。摩擦は仕様として受け入れます。

技術的実現性、権限、スキーマ、プライバシーへの影響に未解決の論点はありません。
